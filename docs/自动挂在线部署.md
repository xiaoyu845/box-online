# 自动挂在线部署

本文讲**部署这件事的原理**：为什么这样分目录、为什么必须用启动器、打包为什么会有副作用、
验证要看什么、出了问题该往哪个方向查。

**本文不含任何命令、脚本或代码。** 具体怎么敲，看执行者的习惯；本文只负责把机理讲清楚。

---

## 一、部署到底在做什么

一句话：**把"面板 + 挂机运行时 + 数据"放到一台常开的 Windows 机器上，让它能长期无人值守。**

由此推出三个必然要求：

1. **机器要常开**，且网络稳定（挂机是长时间保持连接）
2. **数据要有明确的家**（账号库、设置），否则换台机器就"账号不见了"
3. **出问题要能自己恢复**（重启、重连、清理残留），因为没人在旁边守着

部署的所有设计取舍，都是围绕这三条来的。

---

## 二、两个目录的分工

部署后会产生**两个物理位置**，理解它们的区别是理解后面一切的前提：

| | 构建位置 | 运行位置 |
|---|---|---|
| 装什么 | 源码、测试、打包脚本 | 面板程序、挂机运行时、数据 |
| 谁用 | 开发/打包的人 | 真正挂机的机器 |
| 能否拷走 | 一般不拷 | **整包可拷**，换机器直接搬 |

**为什么要分开**：运行位置要能"整个文件夹拷给别人就能用"，那就不能依赖源码目录、
不能依赖开发环境的 Python，也不能把开发用的杂物混进去。

因此运行位置是一个**自包含**的目录：程序、运行时、数据都在里面，拷走即用。

---

## 三、运行依赖为什么是这几个

| 依赖 | 为什么需要 | 少了会怎样 |
|---|---|---|
| Windows | 面板界面、进程操作、窗口控制都建立在 Windows 之上 | 根本跑不起来 |
| Python 运行时 | 开发版直接解释执行；打包版已内置 | 开发版跑不起来 |
| GUI 库 | 面板窗口本身 | 界面起不来 |
| 表格库 | 账号的 Excel 导入导出 | 导入导出失效 |
| Node.js | **轻量挂机模式**的执行体 | 该模式报"未安装" |
| Java 8 | **真实客户端模式**的游戏本体 | 该模式起不来 |
| 外部进服组件 | 登录与进服能力 | 登录、进服全部失败 |

要点：**后三项是"按模式需要"，不是全都必须。**

- 只用轻量模式 → 只需要 Node + 进服组件
- 只用真实客户端模式 → 只需要 Java + 进服组件

部署前先确认打算用哪种模式，可以省掉一半依赖。

## 四、数据落点的原理（最容易出事的地方）

### 为什么会"漂移"

面板需要知道账号库放哪。它有两种可能的答案：

- **便携位置**：运行目录里的数据子目录（我们想要的）
- **用户主目录**：每个用户各自的隐藏目录（历史默认值）

如果**没有明确信号**，程序只能猜。一旦猜错，就会出现"账号不见了"——并不是丢了，
而是读的是**另一个文件**。

### 正确的信号是什么

**启动器在启动面板前，把运行目录和数据目录通过环境变量明确告诉它。**

这就是为什么**必须用启动器启动**，而不是直接双击面板程序：

- 用启动器 → 数据落点确定，不会漂移
- 直接双击 → 可能落到用户主目录，和之前的数据不是一个文件

### 两个必须记住的后果

**① 同一个账号库不能被两个面板同时打开**

两边各自加载一份到内存、各自保存，**后保存的覆盖先保存的**。表现就是"账号莫名其妙变少"。
开第二个面板之前，先关掉第一个。

**② 换机器要连数据一起搬**

只拷程序不拷数据 = 换了台空机器，账号库是空的。

## 五、打包的原理与它的副作用

### 为什么需要打包

目标机器不一定装 Python、也不一定装对了版本。打包做的事就是：
**把解释器、依赖库、我们的代码，全部塞进一个可执行文件**，让对方双击就能跑。

代价是文件变大（几十 MB 量级），换来的是"不需要环境"。

### 单文件程序的运行机制（理解它就理解了三个常见故障）

单文件程序启动时，**先把自身解包到一个临时目录，再从那里运行**。

由此产生三个必然现象：

1. **启动比普通程序慢** —— 每次都要解包
2. **临时目录不可用就起不来** —— 空间不足或没有写权限时，会直接报错退出
3. **被强制结束时，解包目录会残留** —— 正常退出会自己清理，强杀不会

残留目录会持续占空间（每个上百 MB），所以**定期清理是运维的一部分**。
反过来，**尽量用正常退出而不是强杀**，是从源头减少残留的办法。

### 为什么打包会打断正在进行的挂机

打包要替换运行目录里的挂机执行体。而正在执行的挂机**占着那些文件**，替换会失败。

所以打包脚本会**先停掉面板和所有挂机进程**，再替换。

**这一条在协作时最容易被忽略**：打包不是"生成一个文件"这么无害，它会中断线上正在跑的任务。
动手前必须确认对方当前有没有在挂机。

### 为什么启动器不能手改

打包过程会**重新生成**启动器和说明文件。

所以：手改过的启动器会被下一次打包覆盖。**要改启动行为，必须改打包脚本本身**，而不是改生成出来的文件。

（一个已知的典型问题：生成的启动器里窗口显示方式被设成了"隐藏"，
会导致进程在跑但界面看不见。这类问题只能从打包脚本源头修。）

## 六、部署到目标机的原理

### 为什么是"整包拷贝"

因为运行位置是自包含的（见第二节），所以部署的本质是**复制一个目录**：

- 程序、执行体、运行时、数据，全在里面
- 目标机器只需要平台级依赖（如 Java、Node）和外部进服组件

### 为什么仍然推荐用启动器启动

即便程序能双击运行，也**不要**这样做。原因在第四节和第五节：

- 直接双击可能让数据落点漂移
- 启动器还会规避临时目录相关的启动失败

一句话：**双击 exe 是"能用但会出怪问题"的路径；启动器才是正常路径。**

### 部署完必须确认的三件事

1. **界面真的出现了**（进程在 ≠ 界面在）
2. **数据落在预期位置**，且条数对得上
3. **进服组件在运行**（否则后面全是登录失败）

---

## 七、验证的原则

验证不是"看起来正常就行"，而是用**互相独立**的方式确认三件事：

| 验证目的 | 为什么不能只看表面 |
|---|---|
| 产物真的包含这次的改动 | "打包成功了"只说明命令跑完，不说明内容对；必须拿产物和当前源码做**一致性比对** |
| 账号数量真的没变 | **界面上的计数可能读错**（曾经把 22 个读成 2 个，虚惊一场）；必须直接从数据文件数 |
| 界面真的可见 | **进程存在不代表窗口存在**；隐藏窗口的故障只能靠"检测到可见窗口"来确认 |

三条的共同点：**不要相信单一信号。** 每一条都有一个"看起来正常但其实不正常"的陷阱。

---

## 八、运维的原则

| 原则 | 原因 |
|---|---|
| **动数据先备份** | 账号库是唯一不可再生的东西；程序可以重装，号没了就没了 |
| **升级只覆盖程序，不覆盖数据** | 数据在新版本里通常兼容，但覆盖了就回不来 |
| **保留上一个可用的程序** | 新版有问题时能立刻换回 |
| **定期清理临时残留** | 单文件程序的解包残留会一直堆积 |
| **优先正常退出** | 从源头减少残留与数据写坏的风险 |
| **注意同时只开一个面板** | 见第四节 |

## 九、故障的机理与排查方向

按"为什么会这样"来归类，比死记症状更有用：

### 一、进程在，界面看不见

**机理**：启动器把窗口显示方式设成了隐藏。
**方向**：这属于打包脚本的问题，要从源头改，改生成出来的启动器没用（会被覆盖）。

### 二、启动就退出，提示临时目录不可用

**机理**：单文件程序解包失败（临时目录满/无写权限）。
**方向**：清理残留、确认临时目录可写、用启动器启动。

### 三、账号数量变少

**机理**：两个面板同开互相覆盖，或读到了另一个数据目录。
**方向**：先只留一个面板；确认数据落点；用备份恢复。**不要急着重新导入**，那会加重覆盖。

### 四、槽位一直"登录中"不动

**机理**：大量账号同时要求登录，撞上服务端的频率限制，只能排队慢慢过。
**方向**：降低并发（先开少量窗口）；把账号转成可复用的登录凭据，之后就不再需要反复登录。

### 五、反复要求输入验证码

**机理**：验证码没有入口，或信息在传递过程中被丢弃，于是同一个账号被反复重试。
**方向**：用批量预检的方式把需要验证码的账号集中列出、一次填完；
填完的账号应把登录结果缓存下来，避免再次触发。

### 六、报"连接异常"被踢

**机理**：同一个账号出现了**两条**连接。服务端只允许一条，于是断开其中一条。
**方向**：不要重复登录（已有会话就复用）；必须重登时先把旧会话显式注销；
同一账号只允许占一个挂机位。

### 七、打包之后挂机全掉线

**机理**：打包必须先停掉挂机进程（见第五节）。
**方向**：这是**预期行为**，不是故障。协作时提前告知即可。

### 八、选错服务器 / 角色不显示

**机理**：选服靠关键词匹配；关键词不对时会选到错误目标，甚至静默选了第一个。
**方向**：正确行为是**匹配不上就报错**，而不是"凑一个"。

## 十、交接原则

把这套东西交给别人（或交给另一个 agent）时，按这个顺序最省事：

1. **先确认数据在哪**，并记下条数——这是后续一切判断的基线
2. **先备份数据**
3. **确认环境与模式**（用轻量模式还是真实客户端模式，决定要装 Node 还是 Java）
4. **确认外部进服组件可用**
5. **不要一上来就打包**——打包会中断挂机；先问对方现在有没有在跑

---

## 一句话总结

> 部署的本质不是"复制文件"，而是**建立一条确定性的链路**：
> 启动方式确定 → 数据落点确定 → 产物内容确定 → 失败时能自己恢复。
>
> 这条链路上任何一环靠"猜"，后面就会以"账号不见了""界面看不见""无限重试"的形式表现出来。
