# 自动挂在线

> **给谁看**：想把这套装起来用的人；或者直接丢给 AI，让它照做。
> **读完你会知道**：要准备什么 → 怎么启动 → 怎么让号挂上 → 怎么确认真的在挂 → 坏了往哪查。

---

## 〇、它是什么（30 秒）

一个 Windows 桌面面板，用来**同时把多个游戏账号挂在线上**：自动登录、自动进服、
保持在线、到点领在线奖励、领完自动换下一个角色。

一次挂机经过四段：

```
① 登录 ──► ② 进服 ──► ③ 挂在线 ──► ④ 领取 ──► 换角，回到 ②
   ↑
 只做一次（换出凭据后反复复用）
```

**最关键的一句话**：账号密码**只用来换一次凭据**，之后进服全靠凭据。
想清楚这点，后面所有设计（为什么有"转凭据"、为什么要"预热"、为什么会被限流）都顺了。

## 一、你需要准备什么

| # | 需要什么 | 为什么 | 没有会怎样 |
|---|---|---|---|
| 1 | **Windows 10/11 x64**，可长期开机 | 面板与游戏运行时都依赖 Windows | 跑不起来 |
| 2 | **Python 3.13**（命令名 `py -3`） | 开发版直接运行；打包版已内置 | 开发版跑不起来 |
| 3 | **Python 依赖**（界面库、表格库） | 面板界面 + Excel 导入导出 | 界面起不来 / 导入导出失效 |
| 4 | **外部进服组件**（需另行获取） | 提供登录与进服能力，是本系统的地基 | 登录、进服全部失败 |
| 5 | **Node.js 18+**（可选） | 轻量挂机模式的执行体 | 轻量模式报"未安装" |
| 6 | **Java 8**（可选） | 真实客户端模式的游戏本体 | 真实客户端模式起不来 |
| 7 | **账号**（账号密码 / 或已有凭据） | 数据来源 | 没号可挂 |

> 第 5、6 项**按模式二选一即可**：只用轻量模式就只要 Node；只用真实客户端就只要 Java。

**关于外部进服组件**：它是独立程序，面板只通过它的**本地接口**调用。请按其自带说明
获取并启动。本仓库不包含它，也不描述其内部实现。

## 二、第一次跑通（最短路径）

按顺序做，每步都给了"怎么确认做对了"。

### 第 1 步：装依赖

```powershell
py -3 -m pip install -r requirements.txt
```

**确认做对了**：命令正常结束，没有报错。

### 第 2 步：启动外部进服组件

按组件自带说明启动它。

**确认做对了**：组件自己的界面/日志显示"就绪"或在监听。

> 面板启动时会尝试连它；连不上会提示。**不要跳过这一步直接开面板**——
> 那样看到的所有失败都是这一个原因造成的。

### 第 3 步：启动面板

两种方式，选一种：

- **开发版**（在源码目录）：`py -3 run.py`
- **打包版**：双击运行目录里的**启动器**（`.vbs` 或 `.bat`）

⚠️ **打包版请用启动器，不要直接双击 exe。** 原因见第六节：
直接双击会让"数据落在哪"变得不确定，表现成"账号莫名其妙不见了"。

**确认做对了**：窗口真的出现了（进程在 ≠ 窗口在）。

### 第 4 步：导入账号

面板 → **账号库** → 三种方式任选：

| 方式 | 适合 |
|---|---|
| 导入文件 | 已有 CSV / Excel |
| 粘贴导入 | 从别处复制一段文本 |
| 手动添加 | 单个号 |

格式很简单：**登录方式 + 账号 + 密码**（+ 可选备注）。

**确认做对了**：账号库列表里出现这些号，条数和你导入的一致。

### 第 5 步：把账号变成"可复用的凭据"（关键一步）

这一步是把"每次进服都要密码登录"变成"一次登录、长期复用"。

**做法**：账号库 → 选中账号 → **转凭据**（批量可用**一键更新**，
想一次过完所有号就用**预热全部**）。

如果弹出**图片验证码**：在弹窗里照着图填就行。填完的号会变成"就绪"。

**确认做对了**：账号库的"登录方式"列从**密码登录**变成**凭据复用**。

> **为什么要做这一步**：不做的话，每开一个挂机位都要做一次密码登录，
> 十几个位同时上必然触发服务端的频率限制，表现成"全部卡在登录中"。
> 做完之后，进服根本不再碰密码接口，限流跟你无关。

### 第 6 步：开始挂机

工具栏 → **开始挂机**（或首次代理 / 追加挂机）。

**窗口数先从 3~4 起步**，跑稳了再往上加。

**确认做对了**：槽位卡片从"登录中"→"进服中"→"挂机中"，并且**时间在走**。

### 第 7 步：确认真的在挂

看三处，缺一不可：

1. **槽位卡片**：状态是"挂机中"，计时在递增
2. **运行日志**：有"进服成功 / 开始挂机"这类记录，且**没有反复重连**
3. **账号库**：这个号的角色下，在线时长在增长（说明服务端确实认你在线上）

## 三、进服这一层（本版本不含，后续开发）

进服包含两件事：**认证**（让服务器认这个账号）和**跑起来**（进世界、走动、保持在线）。

**本版本只交付后者所需的框架，不含与登录/进服组件对接的实现**：

| 谁 | 状态 |
|---|---|
| 面板、账号库、调度、循环挂角、在线奖励 | ✅ 本版本已包含 |
| 进服对接层（登录、选服、建立连接入口） | 🚧 接口已留，**待后续开发** |
| 执行体（跑起来、挂在线） | 🚧 接口已留，**待后续开发** |

对接层需要提供的能力（保持这些接口就能接上，上层不用改）：

```
登录 → 会话管理（复用/注销）→ 选服 → 选角 → 为挂机位准备连接入口 → 入口就绪判断
```

约定：需要人工验证时抛「需要验证码」并带上图片；其余失败抛统一错误。
细节见 `box_online/bridge.py` 的注释。

### 3.1 两种执行方式（设计目标）

| | 轻量执行体 | 真实客户端 |
|---|---|---|
| 本质 | 只做"进世界 + 走动 + 保持连接" | 真的启动一个游戏客户端 |
| 内存 | 每账号约 75MB 基线（实测） | 每开一个约 1GB |
| 启动 | 快 | 慢 |
| 适合 | 大批量长时间挂机 | 排查"进不去"、需要真实行为 |

两者连的是**同一个连接入口**，所以可以切换对比：
轻量方式进不去时，用真实客户端验证是"链路问题"还是"执行体问题"。

### 3.2 进服的完整动作（目标流程）

```
选服（按关键词匹配，匹配不上就报错，绝不"凑一个"）
  → 选角（指定角色名）
  → 进入世界
  → 走到指定坐标（挂机点/传送门）
  → 进入"挂在线"状态
```

注意"匹配不上就报错"这条：早期是匹配失败就**静默取第一个服务器**，
结果连到了错误的服，表现成"角色不显示"。这类"悄悄走错路"比直接报错危害大得多。

## 四、四条链路是怎么实现的（速览）

### 4.1 登录

三种方式：账号密码 / 直接给凭据 / 官方渠道（邮箱、手机）。

**账号密码的唯一用途是换出一段"游戏侧真正认的凭据"。** 这段凭据只要不被顶掉就一直有效，
所以最优策略是"换一次、长期用"。

登录失败不是一种情况：

| 现象 | 真实原因 | 处理 |
|---|---|---|
| 提示"稍后再试" | **频率限制**（短时间登录太密），几秒就恢复 | 少登录 / 铺开节奏，不是封号 |
| 要求图片验证码 | 需要人工确认一次 | 填图，填完就有凭据了 |
| 密码错误 / 号不存在 | 号本身的问题 | 换号 |

### 4.2 进服

**进服这一步由第三方组件完成**（来源见第三节与致谢），本项目不涉及它怎么做到。

本项目负责的部分是**进服之后的流程**：

```
选服 → 选角 → 进世界 → 走到指定坐标（挂机点/传送门）→ 进入"挂在线"状态
```

> 选服是按关键词匹配的。**匹配不上会报错，不会"凑一个"**——因为凑错服的表现是
> "角色不显示"，比直接报错难查得多。

### 4.3 挂在线

靠**持续维持连接**（回应服务端的心跳）。界面上那个计时 =
**服务端上报的在线时长 + 从采样到现在的流逝时间**，所以它一秒一秒地走。

如果长时间拿不到服务端上报，系统会改用本机时间判断并**明确告警**，
不会静默地永远不换角。

### 4.4 领取

服务端给两条并行的奖励线：**4 个阶段 + 4 个里程碑**，
每个阶段对应两次可领，合计最多 8 次。

- "领过没有"**以服务端返回为准**，不靠本地记账（本地记账一旦不一致就会反复无效领取）
- 到门槛才领；没成功就隔一会儿再试，**不猛刷**
- **四个阶段齐了就换角**（不是等 8 次全领完——里程碑更难达成，等它会长期占住挂机位）

## 五、两种挂机模式怎么选

| | 轻量模式（默认） | 真实客户端模式 |
|---|---|---|
| 是什么 | 只做"进世界 + 走动 + 保持连接" | 真的启动一个游戏客户端 |
| 内存 | 很低，可多开 | 每开一个约 1GB |
| 启动 | 快 | 慢 |
| 适合 | 大批量长时间挂机 | 排查"进不去"、需要真实行为 |

**怎么用**：面板上可以随时切换。

**怎么选**：默认用轻量模式。如果某个号在轻量模式下反复进不去，**切真实客户端试一次**——
能进说明是执行体适配问题，不能进说明是链路/账号问题。这是一个很实用的二分法。

---

### 5.1 一个账号怎么压到 100MB 以内

轻量执行体的内存是**按"进程基线"算的，不是按游戏客户端算的**。实测（Node 26 / mineflayer 4.39）：

| 阶段 | 常驻内存 (RSS) |
|---|---|
| 空 Node 进程 | **约 47 MB** |
| 加载 mineflayer（连带 87 个依赖包） | **约 74 MB** |
| 真实接上服务器后 | 在此基础上增加世界与实体缓存，仍是百 MB 量级 |

对比真实客户端模式：每开一个约 **896 MB**（`mc_xmx_mb` 可调）。

**为什么能这么小**——执行体**不做**这些事：

| 真实客户端要做的 | 轻量执行体 |
|---|---|
| 加载材质、模型、音效、语言包 | 不需要 |
| 构建并渲染整个世界（显存大头） | 不渲染 |
| 加载 Forge 与全部模组 | 不加载 |
| 跑完整的游戏主循环与物理 | 只维护连接与必要状态 |

它只保留"进世界、走到坐标、保持连接、领奖"这几件事所需的状态，
所以内存主要是 **Node 运行时本身 + 协议库**，而不是游戏内容。

**换算成多开能力**：

```
10 个账号（轻量）   ≈ 47MB + 10 × (74−47) ≈ 750 MB 基线
10 个账号（客户端） ≈ 10 × 896 MB          ≈ 9 GB
```

这就是"轻量模式适合大批量"的实际含义：**同样的机器能多挂一个数量级**。

> 注意：47MB 是运行时基线，**每多一个账号不是简单加 74MB**——
> 同机多个 Node 进程会共享一部分系统缓存，实际增量更接近
> "每进程自身的堆 + 连接状态"。真正要控制的是**并发窗口数**，
> 它同时决定登录压力（见第八节排障 1）。

## 六、端口、出口与多实例

### 6.1 每个挂机位有自己的一条链路

进服时，每个挂机位拿到的不是"一个固定的游戏服务器地址"，而是**一个只属于它的连接入口**。

所以：

- 不同挂机位天然走不同入口，互不影响
- 入口背后指向不同的转发目标，就等于**不同出口 IP**
- 面板只认"入口地址 + 端口"，不关心背后是什么

### 6.2 两层都可以配

| 层 | 可配什么 | 典型用途 |
|---|---|---|
| 面板 ↔ 进服组件 | 接口地址与端口 | 端口被占用、组件装在另一台机器 |
| 挂机位 ↔ 游戏 | 每位一个入口 | 不同位走不同出口 |

### 6.3 换出口能解决什么、不能解决什么（重要）

| 限制来自哪个维度 | 换出口有用吗 |
|---|---|
| **同一账号不能有两条连接** | ❌ **完全无效**（这是账号维度，与 IP 无关） |
| 同一台机器上大量账号的共同特征 | ⚠️ 有限（设备与客户端层面的共性不会因为换出口消失） |
| 短时间高频登录 | ✅ 有用，但**性价比低** |

**结论**：换出口是"降低单点压力"的手段，**不能替代**这两件事：

1. **少登录**（先把账号转成可复用凭据）
2. **不重复连接**（同一账号只占一个挂机位）

顺序反了，钱花了但稳定性不会提升。

## 七、日常怎么用

| 时机 | 做什么 |
|---|---|
| 第一次 | 导入账号 → 转凭据（或预热全部，把验证码一次填完） |
| 每天开工 | 看一眼账号库哪些号的凭据失效了 → 刷新 |
| 开挂机 | 先开 3~4 个位，稳了再加 |
| 挂机中 | 看槽位状态 + 日志有没有反复重连 |
| 收工 | **正常退出**，不要强杀（强杀会留下临时残留） |
| 偶尔 | 清理系统临时目录里的残留（每个上百 MB） |

## 八、出问题了怎么查

先记住一条：**看运行日志**。卡片上的状态是结论，日志里才有原因。

| # | 现象 | 真实机理 | 处理方向 |
|---|---|---|---|
| 1 | **一堆位都卡在"登录中"** | 十几个位同时要密码登录，撞上频率限制，只能排队 | 降到 3~4 个位；**先把账号转成凭据**（治本） |
| 2 | **反复要求验证码** | 验证码没入口/信息被丢，同一账号被反复重试 | 用**预热全部**把需要验证码的集中列出、一次填完 |
| 3 | **提示"连接异常"被踢** | 同一账号出现了**两条**连接，服务端断掉其中一条 | 不要重复登录；必须重登时先注销旧会话；**同账号只占一个位** |
| 4 | **进程在，但看不到窗口** | 启动器把窗口设成了隐藏 | 用 `.bat` 启动；或从打包脚本源头修（改生成物会被覆盖） |
| 5 | **启动就退，提示临时目录不可用** | 单文件程序解包失败（临时目录满/无权限） | 清理残留、确认临时目录可写、用启动器启动 |
| 6 | **账号数量变少** | 两个面板同开互相覆盖，或读到了另一个数据目录 | **只留一个面板**；先备份再恢复；**不要急着重导入**（会加重覆盖） |
| 7 | **角色不显示 / 连错服** | 选服关键词不对 | 设置里确认关键词；正确行为是报错而不是凑一个 |
| 8 | **打包之后挂机全掉线** | 打包必须先停掉挂机进程才能替换文件 | 这是**预期行为**，不是故障 |
| 9 | **轻量模式进不去** | 执行体适配问题 | 切一次真实客户端对比，二分定位 |

## 九、边界与风险

**做不到的**

- **同账号并发连接**：服务端按账号判定，客户端侧绕不过
- **彻底消除频率限制**：只能"少登录 + 铺开节奏"缓解

**本项目不做的**

- 伪造登录标识、更换出口来规避服务端对账号的聚簇判定
- 绕验证码
- 注册环节的伪造实名

**需要自己权衡的**

- 批量来的号不牢靠：原号主随时可能登回去，凭据也随之失效
- 集中在一个出口挂大量账号，风控角度比分散更危险
- 长时间高频在线本身就是被关注的特征

---

## 十、直接丢给 AI 时，让它遵守这些

把本文给 AI（如 DeepSeek）让它照着做时，附上这几条，能少走很多弯路：

1. **动手前先确认数据在哪、先备份账号库**——这是唯一不可再生的东西
2. **不要相信界面上的计数**，要从数据文件直接数（界面计数曾经把 22 读成 2）
3. **打包会中断正在进行的挂机**，动手前先问
4. **改了程序之后必须验证产物真的包含改动**（"打包成功"≠"内容对"）
5. **启动器是打包时生成的**，手改会被覆盖；要改就改打包脚本
6. **同一个账号库不要被两个面板同时打开**
7. **文档里不要写外部进服组件的内部实现**（认证方式、协议细节、登录标识路径）
8. 遇到"稍后再试"**不要理解成封号**，那是几秒就恢复的频率限制

## 一句话总结

> **密码只用来换一次凭据；之后靠"凭据 + 每位一条独立链路"把角色挂起来；
> 领奖以服务端为准，四阶段齐了就换角。**
>
> 整条链路真正脆弱的地方只有两个：**账号库**（丢了就没了）和
> **同账号重复连接**（会把自己踢死）。其余优化都排在这两件之后。

### 11.2 挂机执行体

- 轻量执行体：只做"进世界 + 走到坐标 + 保持连接 + 领奖"，内存小、适合多开
- 真实客户端：启动真实客户端，行为最接近真人，便于排查"进不去"

### 11.3 单窗口单 IP（连接入口隔离）

**目标**：让每个挂机位从不同出口连出去，把"同一出口短时间内大量登录"的压力摊开。

**思路**：连接入口本来就是按挂机位分配的，只要让不同位指向不同出口即可，
**不需要改动调度逻辑**，属于部署层面的调整。

**能解决什么、不能解决什么**（这点必须先看清，否则会误判收益）：

| 限制的性质 | 单窗口单 IP 是否有效 |
|---|---|
| 同一出口短时间内高频登录 | ✅ 有效 —— 压力被分散到多个出口 |
| 同一账号不能有两条连接 | ❌ **无效** —— 这是账号维度，与 IP 无关 |
| 同一台机器上大量账号的共同特征 | ⚠️ 有限 —— 机器层面的标识不会因为换出口而改变 |

**成本与前提**：

- 需要与并发窗口数相当的出口资源
- 出口本身的稳定性会直接影响挂机稳定性（抖动会表现为掉线、重连）
- 出口越多，排查问题的成本越高（同一个现象可能是链路问题也可能是出口问题）

**结论**：它是"降低单点压力"的手段，**优先级排在两件事之后**：

1. **减少登录次数**（先把账号转成可复用凭据，能不登就不登）
2. **同一账号只占一个挂机位**（避免自己把自己踢下线）

顺序反了，投在出口上的钱不会变成稳定性。
